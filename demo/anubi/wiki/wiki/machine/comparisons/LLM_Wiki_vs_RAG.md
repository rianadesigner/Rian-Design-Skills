# LLM Wiki vs RAG

## 一句话结论

[[概念_RAG]] 适合“这次问题要基于原文可靠回答”，[[概念_LLM_Wiki模式]] 适合“长期把资料沉淀成可复利的理解系统”。二者不是替代关系，而是互补关系。

## 核心区别

| 维度 | RAG | LLM Wiki |
|------|-----|----------|
| 知识组装时机 | 查询时检索 | 摄入时编译 |
| 知识形态 | 文档碎片 | 结构化互联页面 |
| 状态性 | 偏无状态，每次重新检索 | 有状态，持续积累 |
| 基础设施 | 分块、Embedding、向量库、Rerank | 文件系统、Markdown、LLM Agent |
| 溯源能力 | 强 | 相对弱 |
| 跨文档推理 | 依赖召回质量，通常较弱 | 编译阶段已建立关系，较强 |
| 幻觉影响 | 多影响单次回答 | 错误可能被固化并扩散 |
| 适用规模 | 海量文档、高并发 | 小到中等规模、个人 / 小团队 |

## 适合 RAG 的场景

- 企业内网知识库与客服 FAQ
- 合规制度、金融、政务、工业等强溯源场景
- 表格参数、条款、原始数据保真问答
- 海量文档与高并发服务
- 多用户权限管理和实时更新要求高的系统

## 适合 LLM Wiki 的场景

- 个人笔记与知识管理
- 论文阅读、长期研究项目、小主题深挖
- 需要跨文档综合推理的知识密集任务
- 希望低成本、零服务器、以 Markdown 文件维护的知识库
- 团队 Wiki 的知识沉淀与结构化维护

## LLM Wiki 的关键风险

- **弱溯源**：Wiki 是二次重写结果，可能丢失原文细节。
- **幻觉固化**：错误一旦写入页面，可能经由交叉引用扩散。
- **规模限制**：超大知识库无法只靠索引和上下文窗口维护。
- **协作限制**：纯文件系统不天然支持权限、并发写保护和毫秒级更新。

## 选择建议

- 如果目标是**问得快、查得准、可审计**：优先 RAG。
- 如果目标是**长期研究、整理理解、形成知识图谱**：优先 LLM Wiki。
- 如果既要溯源又要知识复利：采用 [[概念_混合知识架构]]。
